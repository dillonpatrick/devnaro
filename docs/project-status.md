# DevBox — Project Status and Roadmap

> Snapshot recorded on 2026-11-13.
> This document describes the implementation on
> `feat/curated-development-stacks`. Check the branch and CI for live state.

## Current state

DevBox provides a single Debian Trixie Slim development container with a host
CLI, container CLI (`dm`), persistent home, mounted workspace, Docker
integration, Network Manager and VS Code host bridge.

The current stack-aware image build validates one `default` stack. That stack
installs uv as its only stack-managed development tool. The existing Core
dependencies and integrations are retained.

Terraform has been removed from the image, supported stack tools, Zsh plugin
configuration, DevContainer extensions and related tests/documentation. It is
not part of the current DevBox scope.

## Implemented

- Debian Trixie Slim runtime image and Debian-based build stages.
- Python 3.13 runtime for the DevBox CLI (the package supports Python 3.12+).
- Non-root user, Zsh/Oh My Zsh, persistent home and mounted workspace.
- Host CLI lifecycle: start, stop, restart, recreate, recreate-all and clean.
- Container CLI (`dm`) built with Typer and Rich.
- Docker CLI/Compose integration and Network Manager.
- VS Code host bridge and terminal integration.
- Configurable port override file and shell completions.
- Debian package search and package manifest operations:
  `dm tools search/add/remove/list`.
- Build-time validation and warning-and-skip behavior for unavailable optional
  Debian packages.
- Shared host Compose wrapper and terminal helpers.
- Stack Definition schema v2 and Python Stack Resolver with safe YAML loading,
  duplicate-key rejection, strict validation and normalized build artifacts.
- Debian-only stack packages, base image selection, tool version declarations
  and environment.
- Separate DevBox bootstrap uv and stack-provided uv installations.
- Terraform removal from the DevBox image and supported tool configuration.
- Unit tests and CI validation for Python, repository checks and Docker build.

## Current implementation details and limitations

- The `default` stack exists and is selected implicitly by the current Compose
  configuration and Docker build defaults.
- Only uv is supported as a stack-managed tool.
- Tool versions are pinned explicitly; channel-to-version resolution is not
  implemented.
- Docker build stages and the runtime image use Debian-based images; runtime
  package installation uses APT only.
- The selected Debian `BASE_IMAGE` must match the base image generated by the
  stack resolver.
- `dm tools search/add/list` queries the Debian APT indexes included in the
  image.
- `docker/packages.txt` remains a global user package manifest.
- Host CLI, Compose, Network Manager and VS Code bridge still assume one
  DevBox instance.
- Full Docker build and CI validation must be confirmed by the corresponding
  workflow; documentation updates do not imply that validation has passed.

## Current scope

The current maintenance scope is deliberately limited:

1. Keep Debian as the only distribution across the project.
2. Remove Terraform from DevBox.
3. Preserve the existing Core dependencies, integrations and user-visible
   behavior.
4. Keep documentation consistent with the implementation and agreed scope.

Do not add curated development stacks, remove the existing `default` stack,
change stack selection behavior or expand the architecture without explicit
authorization.

## Deferred ideas

The following items are not part of the current scope and remain deferred:

- Multiple curated stacks (Python, Node.js, DevOps and Go).
- Mandatory explicit stack selection and removal of the implicit `default`.
- Additional stack-managed tool installers and channel resolvers.
- Multi-DevBox architecture and multiple named environments.

These ideas must not be treated as implemented or as approved work until
explicitly brought back into scope.

## Architectural guardrails

- Keep Debian as the only supported distribution.
- Preserve the existing Core capabilities and project behavior.
- Keep stack definitions declarative; no arbitrary shell execution.
- Separate Core dependencies from user development tools.
- Avoid broad rewrites and speculative abstractions.
- Create directories and abstractions only when needed.
- Run focused tests, then Python, shell, Compose and Docker validation after
  code changes.
- Keep this document updated as implementation progresses.
- Do not merge pull requests unless the user explicitly asks.
